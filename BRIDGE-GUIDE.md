# TG <-> MAX мост: как устроен и как повторить

Мост между личным Telegram-аккаунтом и мессенджером MAX. Входящие из TG приходят тебе в MAX, ответы из MAX уходят обратно в нужный TG-чат. Три файла внутри одного Python-процесса, без отдельного сервиса.

## Состав

| Файл | Роль |
|---|---|
| `src/tg_bridge.py` | Telethon-юзербот: слушает входящие TG, шлёт их в MAX |
| `src/max_bridge_bot.py` | MAX-сторона: ловит твои ответы/команды в MAX, шлёт в TG |
| `src/bridge_store.py` | SQLite-контракт между ними: маппинг сообщений + состояние |

Зависимости: `telethon>=1.36`, `httpx`. Оба компонента живут в одном asyncio-loop.

## Поток TG -> MAX

1. Telethon подключается к твоему личному TG-аккаунту (api_id/api_hash с my.telegram.org, session-файл создаётся один раз скриптом логина).
2. Хендлер на `events.NewMessage(incoming=True)` фильтрует:
   - личные диалоги - форвардятся всегда (кроме сообщений от ботов);
   - группы - только из whitelist'а (`BRIDGE_GROUP_WHITELIST` в .env, comma-separated chat id);
   - каналы и свои исходящие - игнорируются.
3. Сообщение форматируется как `[Название чата]` + текст и отправляется в твой диалог с MAX-ботом (`send_message` по `user_id` админа).
4. Полученный MAX message id (mid) сохраняется в SQLite: `mid -> (tg_chat_id, tg_msg_id, title)`. Это ключ для обратной маршрутизации.

Детали:
- **Анти-флуд**: больше 5 сообщений из одного чата за 10 секунд - остальные копятся и уходят одной пачкой с заголовком `[Чат] (N messages)`.
- **Медиа** до 20 МБ скачиваются и загружаются в MAX как настоящие вложения (image/video/audio/file). Больше лимита - текстовая заглушка вроде `[фото]`. Медиа обходит флуд-батчер, потому что вложения нельзя склеить в одно сообщение.
- На `attachment.not.ready` от MAX (вложение ещё обрабатывается) - ретрай с нарастающей паузой, до 6 попыток.
- Длинный текст режется на чанки по 4000 символов; в маппинг идёт mid последнего чанка (на него ты и ответишь).

## Поток MAX -> TG

Второго MAX-бота создать нельзя, поэтому мост встроен в основного: главный бот из своего long-poll цикла (`/updates` у бота может читать только один потребитель) вызывает `handle_bridge_update()` для каждого апдейта. Хендлер возвращает `True`, если апдейт принадлежит мосту, иначе апдейт падает в обычную логику бота.

Мост принимает только от админа (`MAX_ADMIN_USER_ID`) и потребляет:
- **reply на пересланное сообщение** - по mid из reply-link находится `(tg_chat_id, tg_msg_id)`, текст уходит в TG как reply на исходное сообщение;
- `/chat <название>` - поиск TG-диалога по подстроке названия, установка «активного чата»;
- `/send <текст>` - отправка в активный чат (обычный текст без команды мост не трогает - он остаётся основному боту);
- `/status` - активный чат + счётчик сообщений за сутки.

После отправки в TG мост подтверждает в MAX коротким сообщением `-> отправлено в <чат>` (реакций в MAX API нет).

## Связка

`bridge_store.py` - единственная точка соприкосновения. SQLite (WAL, отдельная БД, чтобы не конфликтовать с основной), две таблицы: `bridge_map` (маппинг mid -> TG) и `bridge_state` (key-value, хранит активный чат). Записи маппинга чистятся через 30 дней.

Wiring при старте: tg_bridge экспортирует `send_to_tg(chat_id, text, reply_to)` и `resolve_chat(query)`, main.py передаёт их в `max_bridge_bot.configure(...)`. Пока не сконфигурировано - мост неактивен, основной бот работает как обычно. Если session-файла нет или env не заполнен, мост тихо отключается, не валя процесс.

## Env

```
BRIDGE_API_ID=            # с my.telegram.org
BRIDGE_API_HASH=
BRIDGE_SESSION_PATH=data/bridge.session
BRIDGE_GROUP_WHITELIST=   # comma-separated chat id групп
MAX_BOT_TOKEN=            # токен MAX-бота
MAX_ADMIN_USER_ID=        # твой user_id в MAX
```

Логин юзербота - одноразовый интерактивный скрипт (`scripts/bridge_login.py`): вводишь номер, код, 2FA - создаётся session-файл, дальше всё работает без ввода.

## Грабли (важно)

1. **Один session-файл = один клиент.** Никогда не подключайся к тому же `bridge.session` со второй машины, пока работает прод: второй клиент на том же auth key ломает update-поток первого (Telethon падает с фатальной ошибкой десериализации). Нужен дебаг - останови сервис.
2. **Не передавай никому** `.env`, `bridge.session` и `bridge.db` - это полный доступ к твоему TG-аккаунту и переписка. Делиться можно только кодом.
3. Юзербот - это твой личный аккаунт. Telegram не банит за такое чтение своих же сообщений, но массовые рассылки через `/send` делать не стоит.
